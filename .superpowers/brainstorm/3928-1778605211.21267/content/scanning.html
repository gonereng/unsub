Inbox Scanning Pipeline

Three complementary scan mechanisms to catch every subscription, from day one to ongoing.

1. Initial Scan (triggered on account connect)

Gmail: users.messages.list(q: "newer_than:6m AND (unsubscribe OR newsletter OR -announce)")
Outlook: /me/messages?$filter=receivedDateTime ge 2025-11-12&$search=unsubscribe

For each matching email:
→ Parse List-Unsubscribe header (if present)
→ Extract sender domain + name from From header
→ If no header: search HTML body for "unsubscribe" link (regex)
→ Upsert into Subscription table

Runs as a BullMQ job. Status tracked in ScanJob table. User sees progress on dashboard.

Full scan button (for emails older than 6 months):
→ Shows on dashboard after initial scan completes
→ "Scan entire inbox" — paginates through ALL messages
→ Uses Gmail users.messages.list(pageToken) or MS $skip
→ Same detection logic, just no date filter
→ Runs as a separate BullMQ job, user sees progress bar
Risk: may hit provider rate limits on large inboxes. We throttle to 10 req/s with exponential backoff.

2. Real-Time Updates (push-based)

Google

1. Setup: Create Pub/Sub topic + subscription
2. Watch request: users.watch(topicName)
3. On new email: Google pushes notification
4. Webhook receives historyId, fetches changes
5. Check if new sender matches subscription criteria
6. If yes: auto-add to dashboard
Microsoft

1. Setup: Create subscription via
POST /subscriptions
2. On new email: MS sends notification
3. Webhook receives notification
4. Fetch new message details
5. Check List-Unsubscribe + sender
6. If yes: auto-add to dashboard

3. Scheduled Re-scan (cron / fallback)

Why needed: Push notifications can fail. Users may miss the consent screen for Pub/Sub.

BullMQ repeatable job runs every 6 hours per active account:
→ Fetch recent messages since last scan
→ Compare against known subscriptions
→ Add any new ones
→ Update lastEmailAt for existing ones

This also handles the case where a user signs up for a newsletter between push notifications.

Subscription Detection Logic

An email is classified as a "subscription" if ANY of:
1. List-Unsubscribe header present (most reliable — ~70% of newsletters)
2. Unsubscribe link in HTML body (regex: /unsubscribe|opt.?out|cancel.?subscription/i)
3. Sender domain matches known newsletter pattern (e.g., *@mail.*, *@newsletter.*)
4. Same sender sends 3+ emails in 7 days (frequency heuristic) — implemented via a secondary batch analysis after initial scan

Results are upserted. Existing subscriptions are matched by (accountId, senderEmail).

Worker Flow

scan-inbox job (BullMQ) ├── Create ScanJob (status: scanning) ├── Fetch messages from provider API ├── For each message: parse headers + body ├── Upsert subscriptions in batches ├── Categorize subscriptions (keyword → shopping, news, finance, etc.) └── Update ScanJob (status: completed, newCount: N)
